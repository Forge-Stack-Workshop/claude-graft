# Claude API & Agent Orchestration

Patterns for wiring Claude into automated, multi-step systems: role-based
agents, tool/MCP integration, event-driven pipelines, and — the actual
lever that matters — context window discipline.

## When to Activate

- Designing a multi-agent or multi-role Claude workflow (architect, coder,
  reviewer, QA, sync agent).
- Connecting Claude to external systems (knowledge base, code repo, ticketing)
  via webhooks, MCP servers, or tool calling.
- A pipeline's token cost or latency is growing because full documents,
  logs, or conversation history are pasted into every call.
- Deciding between a simple webhook, an MCP tool, and a full agent for a
  given integration point.
- Building a "second brain" / knowledge-base-to-execution pipeline where an
  LLM is the transformation layer between input and output systems.

## Core principle: treat context as a cost, not a convenience

Tokens are wasted the same way in every project: too much irrelevant
history, too much redundant text, implicit reliance on "the model
remembers." It doesn't, and even when a session has memory, unstructured
context degrades answer quality before it exhausts budget.

**Objective:** never hand the model everything you have — hand it only the
active, compressed context needed for the current task.

## Technique 1 — Layered context architecture

Split any system that feeds Claude into four layers, so each has an
explicit boundary:

| Layer | Content | Sent to Claude? |
|---|---|---|
| RAW | Full source data (docs, logs, history) | Never directly |
| COMPRESSED CONTEXT | Structured summary of what's relevant now | Yes — this is the payload |
| MEMORY | Evolving, compact record of decisions/architecture/patterns, updated after each interaction | Only the relevant slice |
| TASK CONTEXT | Current task, required inputs, expected output — nothing else | Yes, always |

The compression step (RAW → COMPRESSED) is where most of the token savings
come from — routinely 80% of the reduction in observed setups.

## Technique 2 — Compressed context template

Use a fixed structure instead of prose dumps. Fixed fields are easier to
compress, diff, and audit than free text:

```text
OBJECTIVE:
...
CONSTRAINTS:
...
CURRENT STATE:
...
WHAT MATTERS:
...
WHAT TO IGNORE:
...
```

Example — turning a long spec + history + notes into a usable payload:

```text
OBJECTIVE: build auth API
STACK: Node + PostgreSQL
CONSTRAINTS:
- OAuth2
- must scale
DECISIONS:
- JWT chosen
- refresh token stored server-side
TASK:
implement the login endpoint
```

## Technique 3 — Stateless interaction pattern

Never assume Claude "remembers" a prior turn or an external document it saw
once. Every call should be self-sufficient:

- Full compressed context included every time.
- Zero dependency on conversation history to fill gaps.
- If state matters, it lives in an external MEMORY artifact (e.g. a
  versioned `current_state.md`), not in the model's short-term context.

This makes calls replayable, cacheable, and safe to parallelize across
agents.

## Technique 4 — Chunking and dynamic injection

Divide context into three tiers per request:

- **CORE** — always included (identity of the task, hard constraints).
- **TASK** — variable, specific to this call.
- **OPTIONAL** — injected only when the task actually needs it (e.g. full
  file contents only for a code-fix task, not for a planning task).

Match what you inject to the task type instead of a fixed bundle:

| Situation | Inject |
|---|---|
| Bug fix | logs + the specific file involved |
| Design task | UI goals + constraints only |
| Architecture task | constraints + system map, not full codebase |

Before each request, prune: remove duplicate context, superseded
decisions, and details unrelated to the current task ("context pruning").

## Technique 5 — Prompt minimal + context payload

Prefer a short, generic instruction plus an external, swappable context
block over one long hand-written prompt per task:

```text
TASK: implement auth API
CONTEXT:
{{compressed_context}}
```

This decouples the *instruction* (stable, reusable) from the *context*
(variable, generated by the compression layer), so the instruction library
stays small and auditable.

## Technique 6 — Choosing the integration mechanism

Three distinct technical layers exist; production systems combine all
three rather than picking one:

| Mechanism | Role | Use for |
|---|---|---|
| Webhooks | Simple triggers | "new item created", "commit pushed", "label added" — fire an event |
| MCP / tool calling | Structured, typed interaction with external systems | Reading/writing specific resources (issues, pages, files) without pasting their raw content into the prompt |
| Agents (multi-step) | Multi-stage logic with intermediate decisions | Pipelines like context-build → design → implement → review → sync |

Rule of thumb: a webhook decides *when* to run something; MCP tools give
Claude *safe, structured access* to a system instead of a text dump;
agents own the *multi-step logic* between those two.

## Technique 7 — Role-based agent pipeline

Instead of one generic call, split work into agents with a narrow mission
each, chained in sequence:

```text
Agent 1 — Context builder   → compress input into the standard template
Agent 2 — Architect         → produce structure/spec/tasks from that context
Agent 3 — Producer          → generate the actual code/content
Agent 4 — Reviewer/QA       → check consistency, flag issues
Agent 5 — Sync              → write a short summary/decision back to the source of truth
```

Each agent receives only the COMPRESSED CONTEXT + its own TASK — never the
full pipeline history.

## Technique 8 — Context Gateway

When multiple triggers feed the same Claude-backed pipeline, add one
intermediate layer in front of every call whose only job is: filter,
compress, prioritize, structure. Without it, each new integration point
tends to invent its own ad hoc context format, and token cost creeps back
up as the system grows.

## Pitfalls

- **Connecting everything directly to Claude.** Wiring a knowledge base or
  code repo straight into the model with no compression step turns every
  call into a full-document dump; cost and hallucination rate both rise.
- **No context standard.** Ad hoc prompt formats per integration make
  pruning and auditing impossible — enforce one compressed-context
  template across the whole system.
- **Assuming implicit memory.** Relying on the model to recall an earlier
  turn or a document shown once produces inconsistent output across
  reruns; make every call stateless and pass state explicitly.
- **Undefined agent roles.** A single "do everything" prompt without a
  named role and a scoped mission produces vague, unreviewable output —
  give each agent one job and one expected output shape.
- **No intermediate validation.** Chaining agents without a review/QA step
  between production and execution lets errors propagate into the
  destination system (e.g. bad code committed, wrong data synced).
- **Automating before the structure exists.** Building triggers and
  pipelines on top of a disorganized knowledge base or repo just automates
  the disorder — fix the structure (context template, memory layer) first,
  then automate.
