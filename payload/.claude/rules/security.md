# Security

- **No secret in the repository.** Ever. Not in code, config, fixtures, tests,
  or commit history. Secrets come from the environment or a secret manager. The
  `secret-scanner` hook blocks the obvious cases; it is a net, not a permit.
- **Every mutating endpoint is authorized explicitly.** An identified caller is
  not an authorized caller: check the role or the ownership, in the endpoint,
  and cover it with a test asserting the denial (403), not only the success.
- **Validate at the boundary.** Every external input — HTTP body, query param,
  header, file, queue message, third-party response — is parsed and validated
  before it reaches the domain. Never trust a shape you did not verify.
- Parameterized queries only. String-built SQL is a defect, not a style.
- Never log a secret, a token, a password, or full personal data.
- An error returned to a client says what to fix, never how the system is built.

## Identity & authorization

- **Per-person data implies a user account.** The moment a product stores
  anything whose value depends on who is looking — preferences, saved views,
  drafts, history, uploads, per-person results — it has real user accounts.
  Ownership is *modelled* (`user_id` foreign key) and every read/write is scoped
  by it in the data layer, never filtered in the UI or trusted from a request
  parameter. Browser storage is a cache, never the system of record. A shared
  password is not an account. Account plumbing — sign-up, sign-in, recovery,
  session expiry, and deletion of the account with its data — ships with the
  first per-person field, not as a later epic.
- **Sign-in goes through the central identity provider first**, behind an
  adapter. The order is: the organisation's SSO (OpenID Connect preferred over
  OAuth 2.x) → an external OAuth provider → a local account as fallback. A local
  account uses a modern password hash (argon2/bcrypt). Because identity sits
  behind an adapter, the product stays deployable against an alternative provider
  or a standalone local mode by configuration.
- **Authorization is resolved against the central directory, never re-declared
  per service.** The SSO is the front door; the organisation's directory
  (LDAP/groups or equivalent) is the source of truth for *who may do what*. A
  service reads a subject's group/role membership and maps it to its own
  permissions, rather than maintaining a parallel authoritative list of admins.
  A right granted or revoked in the directory takes effect everywhere; a local
  role table that shadows it is drift, and a security bug. The directory sits
  behind an adapter (the domain speaks `roles`/`permissions`, not directory
  filters) and is read for authorization only — never a datastore for domain
  data.

## Sessions

- **A session is secured and it expires.** A session that never ends is a
  password that can never be changed. Every authenticated product declares in
  config how long a session lives and enforces it **server-side**.
- Two bounds, both mandatory: an **idle timeout** (inactivity) *and* an
  **absolute lifetime** after which re-authentication is required whatever the
  activity. Idle alone lets a stolen session live forever under a keep-alive.
- The session token is **opaque and server-revocable**: sign-out, password
  change, role change and account deletion invalidate existing sessions
  immediately. Where JWTs are used, access tokens stay short-lived and the
  refresh token is stored server-side, rotated on use, with reuse detection.
- **Cookies over `localStorage`** — `HttpOnly`, `Secure`, `SameSite=Lax|Strict`,
  host-scoped. A token in `localStorage` is readable by any script on the page.
  State-changing requests carry CSRF protection.
- The session id is **regenerated at every privilege change** (sign-in,
  elevation, MFA), generated by a CSPRNG — never derived from a user id or
  timestamp. This is what closes session fixation.
- Expiry is a first-class experience: warn before an idle timeout, preserve
  in-progress work, and return the user where they were after re-authentication.
- Session creation, renewal, expiry and revocation are logged with a correlation
  id, and the log never records the token itself.
